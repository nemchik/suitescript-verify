# Maintaining

Lessons about releasing and developing this repository. They apply to maintainers, not to a project that uses the package, so they live here and not in the shipped README. A lesson about using the package goes in the README section it belongs to.

A maintainer or agent who hits a problem with releasing, the build or the toolchain that is not described here **adds it in the same pull request that found it**: what happened, what it cost, how to avoid it. Keep each entry short and concrete, fix an entry that proves wrong instead of adding a contradicting one, and never put an account number, id or token in it.

- **release-please PRs run no CI checks.** release-please opens its release PR with the default Actions token, and events from that token do not trigger other workflows, so no checks run on it. If branch protection requires checks, the release PR cannot be merged normally, and the first release was blocked. Merge it as an admin, or give release-please a personal access token or GitHub App token so the checks run.
- **Remove `release-as` once the release is made.** release-please keeps `release-as` in its config after use and keeps proposing the same version. Delete it from the config in the pull request that follows the release.- **`npm pack` and `npm test` fail with `EBADDEVENGINES` on a Node patch version that differs from `devEngines`.** The runtime is pinned exactly (`onFail: error`), so a machine one patch behind cannot even dry-run the pack that proves what ships. Switch to the version in `.nvmrc` with your Node version manager, and never loosen `devEngines` to get past it.
- **`npm pack --json` has a different shape in npm 12.** npm 11 prints an array of packages, and npm 12 prints an object keyed by package name. A test that destructures the array passes locally on npm 11 and fails in CI on the pinned npm. Read both shapes (`Array.isArray` first), and run `npx npm@<pinned> ...` before trusting a local pass on anything that parses npm's output.
