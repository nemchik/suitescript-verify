# Lessons

What went wrong running probes through the runner, what it cost, and how to avoid it. An agent that hits a problem with the runner, a deploy, a probe or the sandbox that is not described here **adds it in the same pull request that found it**: what happened, what it cost, how to avoid it next time. Keep each entry short and concrete (the message, the cause, the fix). Fix an entry that turns out to be wrong instead of adding a second one that contradicts it. Never put an account number, id, token or real record id in it.

1. **Every probe change needs a deploy.** The runner's probe list is generated into its dependency list, so a new, renamed or edited probe only exists in the sandbox after a deploy. Write and review **all** the probes of a batch first, dry-run once, and ask for one deploy. A deploy is the person's, in their own terminal, so a wasted one costs a person's time.
2. **A probe that fails at module scope takes the whole runner down.** The runner loads every probe as a dependency of its own `define()`. If one probe's top-level code fails in a way its own `try/catch` cannot capture, the runner never loads and **every** probe returns `HTTP 400` with a message like `com.netsuite.suitescript.scriptobject.ScriptNullObjectAdapter@...` that names no probe. Recover by moving the suspect probe out, dry-running, and asking for a redeploy. Keep module-scope probes rare and tiny, one governed call each, and run them last, one per deploy, so a failure points at one call. Do not keep a probe that is expected to take the runner down; the results page carries its code.
3. **After every deploy, run the chain-proving probe (`probe-zero`) first.** If it fails, the runner is broken (see 2) and no other result means anything.
4. **The role the runner uses is minimal.** A probe that searches transactions or creates a record gets `INSUFFICIENT_PERMISSION`. That error comes after type validation, which is often still evidence, but a probe that needs a record permission should say so in its header, and prefer objects that need no permission (`runtime`, `search.createColumn`).
5. **Check how an API is chained before relying on it.** `crypto.createHash(...).update(...)` returns nothing, so chaining `.digest()` threw `Cannot read property 'digest' of undefined` and cost a deploy. Read the method page for the return type.
6. **Outbound calls rate-limit.** A public echo service answered four requests in a row and failed the fifth with a body that had no `headers`. Keep a probe to four requests or fewer and put the status code in the failure, not just a `TypeError`.
7. **Drafts go stale.** A generated results draft must never overwrite an existing page. After a probe changes, refresh the page's Test and Results sections from the probe and its expected output.
8. **The expectation is the result, not the whole output.** `<slug>.expect.json` holds the `result` object, sorted and indented. Commit it only once the output is stable: a flaky probe reports drift.
9. **An agent's tool can refuse the deploy command.** An auto-mode classifier blocked a deploy dry run chained in one shell line with other commands. Run the dry run alone, and say so if it is still refused; the real deploy is the person's anyway.
10. **Write probes with the file tools, not a shell heredoc.** Backticks, `${}` and quotes in a probe broke a shell heredoc on Windows.
11. **The CLI postinstall exits 3 on a headless machine.** With `SUITECLOUD_CLI_ACCEPT_LICENSE` unset it opens the license with `start`, `open` or `xdg-open`, which fails without a desktop. A desktop install is fine; a headless job needs the maintainer to accept the license, or an install with `--ignore-scripts`.
12. **Never put a user-wide `SUITECLOUD_CI_PASSKEY` in the environment.** It stops browser login in the person's other SuiteCloud projects. Keep it in the project's gitignored env file and hand it to the CLI for its own child process only.
13. **A sandbox refresh clears the token mappings and, presumably, the deployed runner.** If a call fails with an authentication or "not found" error after a refresh, redo the role, mapping and deploy steps.
14. **Use two certificate pairs of different types.** The runner's token is signed ES256 (EC P-256). Oracle's SDK signs the SDF login with PS256 and only parses an RSA key, so that pair must be RSA-4096 with an RSA-PSS certificate (an EC key fails `account:setup:ci` with "There was an error with the private key used to authenticate"). Oracle allows one certificate per integration, role and entity, so the two cannot share a pair.
15. **Token calls need more than the machine-to-machine grant.** With the grant alone the token endpoint issues a token, but every call fails with `401 INVALID_LOGIN_ATTEMPT`. Also enable the token-based authentication flags and the RESTlets and REST Web Services scopes on the integration record.
16. **release-please PRs run no CI checks.** release-please opens its release PR with the default Actions token, and events from that token do not trigger other workflows, so no checks run on it. If branch protection requires checks, the release PR cannot be merged normally and the first release was blocked. Merge it as an admin, or give release-please a personal access token or GitHub App token so the checks run.
17. **Do not hard-code the runner role id.** A fixed role id forced every project to create a role with the package's exact id, and in our experience the id field was read-only after saving a custom role, so a wrong id meant recreating the role. The id is now the `SUITESCRIPT_VERIFY_ROLE_ID` setting; set it to the id of your own role.
18. **Remove `release-as` once the release is made.** release-please keeps `release-as` in its config after use and keeps proposing the same version. Delete it from the config in the pull request that follows the release.
19. **`npm pack` and `npm test` fail with `EBADDEVENGINES` on a Node patch version that differs from `devEngines`.** The runtime is pinned exactly (`onFail: error`), so a machine one patch behind cannot even dry-run the pack that proves what ships. Switch with fnm, which reads `.nvmrc` (`fnm install`, then `fnm use`); never loosen `devEngines` to get past it.
